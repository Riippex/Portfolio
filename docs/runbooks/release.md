# Release runbook

This document defines the release gates, pre-flight checklist, privacy and data classification audit, cost boundary review, end-to-end smoke verification, and owner authorization procedures for releasing the portfolio.

## Release Governance and Boundary

- **Integration vs Release**: `develop` is the active integration branch. `main` is the strict release boundary.
- **Authorization Gate**: Promoting `develop` to `main`, publishing a git release, or deploying production infrastructure requires explicit owner authorization. No agent or automated tool may merge into `main` or update `main` autonomously.
- **Zero-Downtime & Rollback**: Cloud Run and Cloudflare Workers both support atomic instant revision traffic switching. In case of regression, traffic is immediately switched to the previous known-good revision.

## Pre-flight Checklist

Before initiating a release to production:

- [ ] Working tree is clean (`git status` reports no untracked or modified files).
- [ ] All unit, architecture, and published smoke tests pass in Release configuration:
  - Backend: 286+ unit tests, 10 architecture tests, published integration smoke test.
  - Frontend: 75+ Vitest tests across 10 test suites, ESLint clean (0 errors, 0 warnings).
  - Next.js 16 production build compiles all routes without warnings.
  - Vinext Cloudflare Workers bundle builds cleanly for both `dev` and `prod`.
- [ ] Infrastructure definitions are validated:
  - `tools/check-deployment.mjs` passes (17 files, 75 mutation tests).
  - `tools/check-terraform-plans.mjs` passes (offline plan proofs hold).
  - `tools/check-release.mjs` passes (privacy, evidence, cost, and release invariants hold).
- [ ] Agent skills are synchronized: `pwsh tools/sync-agent-skills.ps1 -Check` passes.
- [ ] No private files (`documents/`, `.env`, machine configs) or raw credentials are staged or committed.

## Privacy & Data Classification Audit

The portfolio strictly adheres to the [Data handling policy](../data-handling.md):

| Data Class | Portfolio Capability | Processing & Storage Lifecycle |
|---|---|---|
| **Public Evidence** | Biography, case studies, citations | Versioned public files in `docs/evidence/`. Persisted durably in git; bundled into container at publish time. |
| **Durable Operational Records** | None | Zero application persistence: no database, no durable disk, no transaction logs. |
| **Session-transient Input** | Chat turns, vacancy text, contact messages | Processed strictly in memory for the duration of the HTTP request. Discarded immediately upon completion. |
| **Short-lived Control State** | Rate limit buckets, Turnstile tokens | In-memory sliding window cache with TTL eviction. Discarded on expiry; lost harmlessly on container restart. |
| **Sensitive Ephemeral Material** | Visitor name, email address, message body | Validated, bounded (64 KiB body limit, 5000 char message), and relayed via Cloudflare REST API. Never logged, cached, or persisted. |
| **Secrets & Credentials** | API tokens, HMAC proxy identity secret | Stored in GCP Secret Manager and Cloudflare Workers secret bindings. Never embedded in code, git, or client bundles. |

### Privacy Invariants Verified

1. **Relay-only contact delivery**: The contact service (`Rafael.Portfolio.Modules.Contact`) has zero database access, creates no delivery receipts in storage, and logs only outcome status codes and latencies.
2. **Stateless AI assistant**: The assistant service (`Rafael.Portfolio.Modules.Assistant`) maintains no chat history, user profiling, or cross-request sessions.
3. **Ephemeral job matching**: Vacancy text and match analysis (`Rafael.Portfolio.Modules.JobMatching`) exist only in memory during the request.
4. **Signed edge identity**: In production (`ASPNETCORE_ENVIRONMENT=Production`), all interactive endpoints strictly enforce HMAC-SHA256 signed identity headers (`X-Client-Key-Proof`) generated by the Cloudflare edge proxy.

## Cost Review & Monthly Budget

Infrastructure is architected to operate well within free tiers, with zero baseline compute or storage overhead:

| Service / Resource | Configuration | Free Tier Allowance | Estimated Monthly Cost |
|---|---|---|---|
| **Google Cloud Run** | `min_instances = 0`, `max_instances = 2`, 1 vCPU, 512 MiB | 2M requests/mo, 360,000 vCPU-seconds, 180,000 GiB-seconds | **$0.00** (scale-to-zero when idle) |
| **Google Artifact Registry** | Docker format, immutable SHA tags | 0.5 GB free storage | **~$0.10** / month |
| **Google Secret Manager** | 3 secrets (`turnstile`, `proxy-identity`, `contact-token`) | 6 active secret versions, 10,000 access operations/mo | **~$0.18** / month |
| **Cloudflare Workers** | 2 environments (`dev`, `prod`), Vinext bundle | 100,000 requests / day (Free tier) | **$0.00** |
| **Cloudflare Turnstile** | Managed mode widget | Unlimited site evaluations | **$0.00** |
| **Data Persistence** | None (no Cloud SQL, no Firestore) | N/A | **$0.00** |
| **Total Estimated Cost** | Full portfolio stack | — | **< $0.50 USD / month** |

### Cost Mitigation Controls

- **Scale-to-zero defaults**: Cloud Run `min_instances` is hardcoded to `0`, ensuring zero idle spend.
- **Bounded burst limit**: Cloud Run `max_instances` is capped at `2` to prevent runaway scaling during denial-of-service or bot traffic.
- **Rate limiting**: In-memory rate limiting (10 req/min for assistant/jobs, 3 req/10min for contact) throttles abusive traffic at the application layer.
- **Edge protection**: Cloudflare Turnstile blocks automated bots before request execution.

## End-to-End Release Smoke Execution

Run the complete offline smoke and release verification suite:

```bash
# 1. Release Invariants & Privacy Audit

# 2. Deployment Invariants & Workflows
node tools/check-deployment.mjs

# 3. Offline Terraform Plan Proofs
node tools/check-terraform-plans.mjs

# 4. Backend Published Integration Smoke (HTTP server lifecycle outside checkout)

# 5. Frontend Multi-stage Worker Verification

for stage in dev prod; do

  node ../tools/check-wrangler-build.mjs $stage
  npx wrangler deploy --dry-run --env $stage --var PORTFOLIO_BACKEND_URL:https://backend.example.test
done
cd ..

# 6. Skill Synchronization Verification
pwsh tools/sync-agent-skills.ps1 -Check
```

## Release Promotion Procedure (Owner Only)

Once all pre-flight checks and smoke executions pass on `develop`:

1. **Verify `develop` is clean and up to date with `origin/develop`**:
   ```bash
   git checkout develop
   git pull origin develop
   ```
2. **Promote `develop` to `main` via fast-forward merge**:
   ```bash
   git checkout main
   git merge --ff-only develop
   ```
3. **Tag the release**:
   ```bash
   git tag -a v1.0.0 -m "Release v1.0.0: initial public portfolio release"
   ```
4. **Push `main` and tag to origin**:
   ```bash
   git push origin main --tags
   ```
5. **Trigger deployment workflow**:
   - In GitHub Actions, navigate to **Deploy**.
   - Dispatch `deploy.yml` with `environment: prod`.
   - Review and approve the deployment in the GitHub environment gate.

## Rollback Procedure

If any issue is detected after production release:

1. **Backend Rollback (Cloud Run)**:
   - In Google Cloud Console or via `gcloud`, route 100% traffic back to the prior revision:
     ```bash
     gcloud run services update-traffic rafael-portfolio-backend --to-revisions=<PREVIOUS_REVISION>=100 --region=us-central1
     ```
2. **Frontend Rollback (Cloudflare Workers)**:
   - In Cloudflare Dashboard (Workers & Pages > Deployments), roll back to the previous deployment ID instantly, or re-deploy the previous release commit.
